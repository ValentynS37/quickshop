# BADS AI Administrator — Pilot Launch Plan

## Purpose

BADS AI Administrator is the first commercial demonstration of BADS TrustOS for ordinary business operations.

It converts an inbound request into:

1. structured intake;
2. lead qualification;
3. a proposal draft;
4. a project backlog;
5. an evidence package;
6. a human approval decision.

The pilot is intentionally human-in-the-loop. It does not send messages, sign documents, spend money, delete data or deploy code without an explicit approval step.

## Commercial position

This is an **AI automation service with a TrustOS evidence layer**, not the final enterprise TrustOS license.

The client buys a measurable workflow result:

- fewer manually processed requests;
- faster first response;
- fewer missed tasks;
- a daily management summary;
- an audit trail for every AI-assisted action.

## Demo flow

1. Client request is entered through a safe demo form.
2. Intake Agent extracts facts and required fields.
3. Qualification Agent scores fit, urgency and risk.
4. Proposal Agent creates a scoped commercial draft.
5. Project Agent creates implementation tasks and acceptance criteria.
6. Evidence Agent records the input fingerprint, policy version, decisions and output.
7. The owner approves or returns the draft for revision.

Demo file: `ai-admin.html`.

## Three pilot targets

### Pilot 1 — Amazinum

**Reason:** warm AI/data-science contact and the shortest route to technical feedback.

**Pilot scenario:** intake and qualification of AI project requests, preparation of a discovery brief, risk questions and an evidence-backed handoff to a human consultant.

**Offer:** discounted implementation in exchange for structured feedback, a testimonial and permission to publish an anonymized case study.

### Pilot 2 — BIG Language Solutions / 911 Interpreters workflow

**Reason:** the user already understands interpreter onboarding, vendor communication, payment questions and support flows.

**Pilot scenario:** classify vendor requests, prepare approved answer drafts, detect missing onboarding documents, create follow-up tasks and generate a daily operations summary.

**Boundary:** no autonomous tax, legal, payroll or contractor-status decisions.

### Pilot 3 — UFuture / innovation ecosystem workflow

**Reason:** relevant innovation and startup ecosystem with a clear flow of applications, partnership requests and project reporting.

**Pilot scenario:** startup or partnership intake, qualification, evidence-backed summary, routing to the correct team and portfolio reporting.

**Boundary:** no autonomous investment decision or applicant rejection.

## Pilot KPI

Each pilot must select one primary KPI before implementation:

- median first-response time;
- percentage of requests correctly classified;
- number of manual steps removed;
- percentage of drafts accepted without major revision;
- number of missed follow-ups;
- management-report preparation time.
